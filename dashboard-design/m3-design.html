Loku Tuning — M3 Boundary Design

M3 境界設計書 — タグ＋ID結合の実装

位置づけ：design-spec.html のマイルストーンM3詳細版　対象：広告/GBP/SNS → LP → LINE友だち化 → 因果診断 → 承認配信の一気通貫をモニター店舗の実LPで成立させる工程
M3の要点： M2まではデモ環境（handoff-demo）で完結していたが、M3は3者（Daiya／Loku本体・社長／モニター店舗）が絡む初めてのフェーズ。誰が何を持つかを先に切り分けないと「デモではできたのに実店舗で動かない」が起きる。この文書はその境界線を固定するための設計書。

1. M3のゴール

下記の一気通貫を、モニター店舗の実LP上で成立させる。

広告／GBP／SNS→ LP（loku-attn.jsタグ・lt_src/lt_ad捕捉）→ LINE友だち化（anon_id→予約リンク→friend_id結合）→ 因果診断→ 承認配信

M2までは handoff-demo/app.mjs のインメモリストアで anon_id ↔ friend_id の結合・同意ゲート（consent_record）・因果診断までを動作確認済み。M3で結合部分を実LP・実LINEアカウントに繋ぎ、デモの配線を本番の配線に置き換える。

2. 3層の境界表（M3の核）

「誰が何を作る/持つか」で3層に切る。層Aを自力で全部終わらせてから層Bを依頼し、層Bの回答を待つ間に層Cの受け入れ準備を進める、が基本の進み方（詳細は4章）。

A

デモ環境だけで完成できるもの

担当：Daiya（このリポジトリ内で完結）
Loku本体にもモニター店舗にも依存しない。今すぐ着手・完成できる。
  • タグ本体（loku-attn.js）
    1stパーティ anon_id 発行・localStorage併用・7日揮発前提。既存LPにhead1行を足すだけで動く後付け設計を維持する。
  • lt_src・lt_ad パラメータ捕捉
    広告用リンク（画面5 POST /setup/ad-linksで発行）のURLパラメータをタグが読み取り保存。LINE内ブラウザのITP・Cookie制限を受けないURL運びの経路として既に設計済み。
  • IntersectionObserverブロック計測
    BOX_ORDER（hero/problem/beforeafter/staff/pricing/voice/faq/cta）単位の注視・離脱を計測。画面2「LP注目マップ」の元データ。
  • sendBeacon離脱フラッシュ
    タブクローズ・遷移時に取りこぼしなく計測データを送る仕組み。
  • 結合API（anon_id → friend_id）
    POST /api/attn/merge 相当（app.mjs 452行目付近）。consent_record（obtained_by・method・未成年時は guardian_consent 必須）が揃わないと consent_record_complete=false のまま結合を保留するゲートを既に実装済み。M3ではこのAPIを実サーバーへデプロイするだけで、ロジック自体の新規実装は不要。
  • 既存LPへの後付けブロック推定
    画面5「セットアップ」＝AIがLPのHTML構造からブロックを自動推定→店主が10秒で目視確認・修正するUI。POST /setup/infer-boxes / PUT /setup/box-mapping。
B

Loku本体／社長（奥村航稀）の協力が要るもの

担当：Loku本体（社長依頼はpending・下の再現マップで自力進行を優先）
Daiya側だけでは完成できない前提だったが、Loku既存機能で代替できる経路が見つかったため、下記3件の社長依頼は保険（pending）に格下げする。まずは既存機能での再現マップを進め、詰まった時だけ依頼を起こす。
alt_route既存Loku機能での再現マップ（社長依頼せずに進める経路）
  • ① LIFF（登録済）でanon_id×userId結合
    友だち追加時のfriend_id払い出しWebhookを新設しなくても、既に登録済みのLIFFエンドポイントを経由すれば、LIFF起動時に取得できるLINEのuserIdと、LP側で発行済みのanon_idをその場で結合できる。層Bの2件目（friend_id払い出しWebhook）の代替経路になる。
  • ② トラッキングURL（uid=LINE→LP再訪の実名捕捉）＋流入経路＋MCP友だち管理
    Loku既存のトラッキングURL機能はuidパラメータ付きでLPへ再訪させられるため、LINE配信→LP再訪の経路で実名（friend_id）側からLP行動を捕捉できる。予約リンクへのanon_idパラメータ通過（層Bの1件目）を待たずとも、流入経路の記録とMCP友だち管理を組み合わせれば同等の帰属が取れる可能性がある。
  • ③ MCP APIキー配信（Bearer lk_）
    送る承認箱の下書きをLoku本体の実配信に渡す経路（層Bの3件目）も、新規Webhookを依頼する前に、既存のMCP APIキー（Bearer lk_）配信経路で送信キューから直接LINE配信を叩けないかを先に検証する。
help残確認2点（再現マップを進める上でのブロッカー）
  • LIFFエンドポイントのホスト方法
    ①の結合をLoku Tuning側で完結させるには、LIFFエンドポイント（結合ロジックを載せるページ）をどこにホストするか（Loku Tuning側のドメインで持てるか／Loku本体側のみか）が未確認。
  • MCPのアクティブアカウント固定の罠
    MCP経由の操作はアクティブアカウント固定で動く仕様（おく社内ルール教科書でも既知の注意点）。③のAPIキー配信・送信経路をモニター店舗ごとに正しく向けられるか、アカウント切替の運用が未確認。
pending社長依頼（保険・pending扱い）
  • 〔pending〕予約リンクへの anon_id パラメータ通過
    現状の予約リンクは l.oku-ai.co.jp/r/<id> 固定形式。②のトラッキングURL経路で代替できなかった場合のみ依頼する。
    依頼の一文（保険）：「予約リンク（l.oku-ai.co.jp/r/<id>）に、LP側で発行したanon_idをパラメータとして付けて渡し、友だち追加完了時にそのanon_idを一緒に受け取れるようにしていただけますか。」
  • 〔pending〕友だち追加時の friend_id 払い出しWebhook
    ①のLIFF経路で結合が成立すれば不要になる想定。LIFF経路で詰まった場合のみ依頼する。
    依頼の一文（保険）：「友だち追加が成立したタイミングで、そのfriend_idと直前に受け取ったanon_idのペアを、こちらが指定するエンドポイントにWebhookで送っていただけますか（本文はJSONで {anon_id, friend_id, added_at} の3項目のみで構いません）。」
  • 〔pending〕AI配信（撃つ側）への因果セグメント受け渡し
    ③のMCP APIキー配信経路で送信キューから直接叩けなかった場合のみ依頼する。
    依頼の一文（保険）：「店主が承認済みにした下書き（friend_id・本文・送信予定タイミング）を渡すので、それをLINE配信として実際に送る窓口（APIかWebhook）を用意していただけますか。」
C

モニター店舗側に必要なもの

担当：モニター店舗オーナー
募集時のチェックリストで先に確認する（3章）。
  • LP（既存で可）
    headにタグ1行を追加できること。新規LP制作は不要。
  • LINE公式アカウント
    友だち追加の受け皿として保有していること。
  • Loku導入（または導入意思）
    未導入の場合はモニター参加と同時に導入を条件とする。
  • モニター同意
    計測・LINE結合・データの使い途への同意（3章参照）。

3. モニター募集方式（1スタジオ目の経路変更・2026-08-24 Daiya決定）

経路を「YUKIさん1社への個別提案」から「コミュニティ内の無料モニター募集（複数店並列）」へ切り替える。

route募集経路
はじめて.AI（Daiya所属コミュニティ）→ 無料モニター募集案内 → 応募（複数店舗を並列で受け入れ）
priority_high優先枠

ピラティス／パーソナルジム（pilatesプリセット適合）を優先枠とする。他業種の応募は受け入れるが、因果コード辞書（judo温存済みの既定プリセット）が業種特化のため参考データ扱いとし、楔（Loku Tuningの主戦場を絞る方針）を崩さない。

checklist募集要件チェックリスト
check_box_outline_blankLP有無（既存URLがあるか。なければ導入時に簡易LP代替を検討）
check_box_outline_blankLINE公式有無（未保有なら開設意思があるか）
check_box_outline_blank月間流入の目安（LP訪問が月100件未満だと因果診断のサンプル数が不足しやすい旨を事前共有）
check_box_outline_blank業種（ピラティス／パーソナルジム＝優先枠、それ以外＝参考データ扱いである旨を事前共有）
verified_userモニター同意の要点
同意項目店主に説明する内容対応するcompliance資産
計測内容の明示LP上での滞留・離脱・注視ブロックを匿名IDで計測する旨タグ本体（層A）・consent_record
LINE結合の同意予約リンク経由で匿名IDとLINE友だちを紐付ける旨。同意情報（誰が・どの方法で取得したか）を記録するPOST /api/attn/merge の consent_record（obtained_by / method / guardian_consent）
opt-out友だちがいつでも配信停止・プロファイリング拒否できる旨POST /api/attn/opt-out・POST /api/attn/profiling-opt-out
データの使い途診断・下書き作成にのみ使い、送信は必ず店主の承認を通す旨（画面3の思想）buildDisclosure（開示文生成）・画面3「送る承認箱」
無料の対価＝事例化許可モニター期間中の利用料は無料とする代わりに、事例として紹介する許可をいただく。店名は匿名可とし、強制はしない募集文・同意書に別途明記（本設計書の対象外）

募集文そのものはここでは作らない。方式決定（本章）を踏まえ、別途Daiyaが指示する。

4. M3実装順

層Aを先に全部終わらせる → 層Bを依頼して待つ間に層Cの受け入れ準備を進める → 層Cを受け入れる、の順で進む。層Bの回答待ちで手が止まらないよう、層Cの準備は層B依頼と並行する。

1
層Aを実サーバーへデプロイ
handoff-demo のインメモリ実装（app.mjs）を永続ストレージ（DB）に載せ替え、実LPから叩ける本番エンドポイントとして立てる。タグ本体（loku-attn.js）も配布可能なCDN/静的ホスティングに置く。
check_circle完了判定：任意のテストLPにタグ1行を貼り、anon_id発行・ブロック計測・sendBeacon離脱送信が本番エンドポイントに届くことを確認できた時
2
層Bを社長へ依頼（2章の3件）
予約リンクへのanon_id通過→友だち追加Webhook→AI配信への受け渡し、の順で依頼。1件目が通らないと2件目の検証ができないため、順番に確認しながら進める。
check_circle完了判定：テストLP→予約リンク→LINE友だち追加を実際に行い、anon_idとfriend_idのペアが層AのDBに届いて結合が成立した時
3
層Cの受け入れ準備（層Bと並行）
3章の募集要件チェックリスト・同意の要点をもとに、Daiyaが別途、募集文とモニター同意書のたたきを作る（本設計書の対象外）。募集経路（はじめて.AI）への案内文の下書きも並行して進めて良い。
check_circle完了判定：募集文・同意書のたたきが揃い、いつでも募集を出せる状態になった時
4
モニター1店舗目の受け入れ・実地確認
層1〜3が揃った状態で最初のモニター店舗を受け入れ、画面5のセットアップフロー（タグ設置→ブロック自動推定→広告リンク発行）を店主と一緒に完走する。
check_circle完了判定：モニター店舗の実LPで「LP訪問→LINE友だち追加→因果診断→承認箱への下書き投入」が実データで1周した時（＝M4「モニター店舗で実運用」への移行条件）
