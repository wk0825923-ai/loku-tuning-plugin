層B検証手順書（LIFF疎通／MCP・APIキー疎通）

対象：Daiya本人がLINE Developers・Loku設定画面・スマホLINEを実際に操作して確認する。所要目安：LIFF検証15〜20分／MCP検証10分。
目的： 「LP訪問者（anon_id）」と「LINEの友だち（userId）」をID結合できるか、また店舗ごとにAI連携（MCP／APIキー）が安全に切り替えられるかを、実機で確かめる。ここが通れば、LP→LINE友だち→承認配信→再訪捕捉の一気通貫が「絵に描いた設計」から「動く土台」になる。
LP訪問（anon_id発行）→ LIFFを開く（?anon_id=…）→ userId取得・結合→ 友だち追加→ 承認配信（画面3）→ 再訪はトラッキングURLのuidで実名捕捉

検証① LIFF疎通

LIFF を使って、LP上のanon_idとLINEのuserIdが同じ画面で同時に取れるかを確認する。

  1. LINE Developersでチャネルを確認する
    developers.line.biz/console にログインし、Loku Tuning用（またはモニター店舗用）のチャネルを開く。「LIFF」タブがあることを確認。
    check_circle期待：LIFFタブが存在し、「追加」ボタンが押せる状態
    error失敗時：チャネルが見当たらない／権限がない → Loku側の管理者権限を確認してから再試行
  2. LIFFアプリを追加し、エンドポイントURLに検証ページを登録する
    「追加」→ LIFFアプリ名を入力 → サイズは「Full」推奨 → エンドポイントURLに、これから作る検証ページのVercel URL（例：https://loku-tuning-plugin.vercel.app/dashboard-design/liff-test.html）を入力。スコープは profile を選択（profileスコープがないとuserIdの取得元＝getProfile()が使えない）。「友だち追加option」は検証段階では「On（通常）」を選ぶ（後述の④参照）。
    check_circle期待：保存後、liff.line.me/xxxxxxxx-xxxxxxxx形式のLIFF URLとLIFF IDが発行される
    エンドポイントURLの要件（URLスキームはhttps必須、URLフラグメント不可、liff.init()はエンドポイントURL以下の階層でのみ動作）： LINE Developers - Registering LIFF apps
  3. スマホのLINEでLIFF URLに?anon_idを付けて開く
    発行されたLIFF URLの末尾に ?anon_id=test123 を付けてスマホに送る（LINEのトーク画面に自分宛メモとして貼るのが簡単）→ タップして開く。
    check_circle期待：liff-test.html画面が開き、userId（プロフィール取得を許可した場合）とanon_id=test123が両方表示される
    error失敗時：白画面／エラー表示 → LIFF IDが正しいか、エンドポイントURLがVercelに実際にデプロイ済みか確認
    クエリパラメータの引き継ぎ：LIFF URLに付けた追加情報はliff.stateとしてリダイレクト後のURLに引き継がれ、liff.init()がこれを元に初期化する。SDK側で付与されるパラメータ（liff.state・access_token等）は、init完了前に自分で書き換えないこと。 LINE Developers - Opening a LIFF app
  4. userId取得の条件を確認する（ログイン／同意／LINE内ブラウザ）
    画面に表示されたuserIdが空でないか確認。空の場合は以下を切り分ける。
    • PCブラウザや外部ブラウザで開いた → liff.isInClient()がfalseになりログイン状態に依存（外部ブラウザではLINEログインを別途要求）
    • profileスコープの同意画面でユーザーが拒否した → getProfile()が失敗する
    • liff.getContext()のuserIdはhelp未確認：常にログイン済みユーザーのuserIdを返すか、匿名アクセス時は空になるかの厳密な条件は一次情報で明言箇所を特定できなかった。実機で①LINE内②profile許可済③LINEログイン済の状態にして表示されるかを本検証で確認する
    check_circle期待：LINE内ブラウザ・profile許可済みの状態でuserIdが取得できる
    getProfile()にはprofileスコープが必須。getContext()はtype/userId/viewType/accessTokenHashを含むコンテキスト情報を返す： LINE Developers - Using user data in LIFF apps and servers
  5. 友だち追加の導線を確認する
    LIFFアプリ設定の「友だち追加option」は3種類：On（通常）＝許諾画面に友だち追加のチェックが並ぶ、On（aggressive）＝許諾画面のあとに追加確認の別画面が出る、Off＝表示しない。まずは通常（On）で試し、友だち追加チェックが実際に許諾画面に出るか確認する。
    check_circle期待：初回アクセス時の許諾画面に「LINE公式アカウントを友だち追加」のチェックボックスが表示される
    error失敗時：出ない → 既に友だちの場合は表示されない仕様の可能性。一旦ブロック→解除して再テスト
    追加オプションの仕様（通常／aggressive／Off）： LINE Developers - Registering LIFF apps　／　既存の友だちに再度追加を促す新API liff.requestFriendship()： LINE Developers Tips - request-friendship

事前調査ファクトチェック一覧（出典付き）

項目結果出典
(a) LIFFエンドポイントURLに任意の自前HTTPSドメイン（Vercel等）を登録できるか できる。要件はhttpsスキームであることとURLフラグメントを含まないことのみ。ドメイン自体の制限（Vercel不可等）の記載は確認できなかった Registering LIFF apps
(b) LIFF URLのクエリパラメータの引き継ぎ挙動 URLに付けた追加情報（クエリ含む）はliff.stateとしてリダイレクト先URLに引き継がれ、liff.init()がこれを解決する。init解決前にSDK付与パラメータを書き換えないこと、と明記あり Opening a LIFF app
(c) getProfile()/getContext()でuserIdを取る条件 getProfile()はprofileスコープの許諾が必須。getContext()はtype/userId/viewType/accessTokenHashを返す。LINE内ブラウザか外部ブラウザかでログイン要求の有無が変わる（外部ブラウザは別途LINEログインが必要）という一般仕様は確認できたが、getContext()のuserIdが未ログイン状態でも取れるかの明言箇所はhelp未確認 Using user data in LIFF apps and servers
(d) 友だち追加の導線 LIFF追加時の「友だち追加option」＝On（通常）／On（aggressive）／Offの3種。加えて2026年にliff.requestFriendship()という能動喚起APIが追加された（ブロック解除の再喚起にも使える） Registering LIFF apps／request-friendship Tips

検証② MCP／APIキー疎通

MCP 接続とAPIキーが、モニター店舗運用（複数店を同時に見る）に耐えるかを確認する。既知の罠＝MCPが「アクティブアカウント固定」でサポート用LINEに載っている点（メモ参照）を実機で裏取りする。

  1. Loku設定→AI連携→APIキー作成
    Loku管理画面の設定 → AI連携（またはAPI/インテグレーション）タブを開き、新規APIキーを発行する（Bearer lk_…形式）。スコープが選べる場合は読み取り系のみを選ぶ（送信系は今回は叩かない）。
    check_circle期待：lk_で始まるキーが発行され、一度だけ表示される（再表示不可の場合はこの場でメモ）
  2. curlで疎通を確認する（読み取り系のみ）
    発行したキーで、友だち一覧など読み取り系エンドポイントに1回だけ疎通確認する。 
    # 例：友だち一覧の疎通確認（読み取り専用）
curl -s -H "Authorization: Bearer lk_xxxxxxxxxxxx" \
  "https://api.oku.jp/v1/friends?limit=1"
    check_circle期待：HTTP 200・JSONが1件返る
    error失敗時：401/403 → キーのスコープ不足かアカウント紐付け違い。404 → エンドポイントURLが実際のLoku API仕様と異なる可能性（この手順書のURL例は仮。実際のAPIリファレンスで要確認）
  3. 罠の確認：MCPはアクティブアカウント固定か
    既知メモ：「⚠️MCPはアクティブアカウント固定でサポート用LINEに載る（おく本体でない）」。これをこのタイミングで再現確認する。
    • Claude側のMCP接続設定を開き、現在つながっているLINEアカウントが「サポート用LINE」か「おく本体」かを確認
    • モニター店舗Aの情報を読み取り → 続けてモニター店舗Bへ切替可能か試す（設定画面上でアカウント切替UIがあるか）
    • 切替UIがない場合：1接続＝1アカウント固定と確定させる
    check_circle期待（想定シナリオ）：アクティブアカウント固定が再現される＝店舗ごとにMCP接続を別立てする必要があると確定
  4. 複数店舗運用の場合の運用案
    アカウント固定が確定した場合の対処案（本検証で優先度を確定させる）：
    • 案1：店舗ごとにAPIキー（Bearer lk_）を分けて発行し、curl/HTTP直叩きはキー切替だけで済ませる（MCP経由の対話操作はしない）
    • 案2：モニター店舗が2〜3店の間はMCP接続先アカウントを都度手動切替（Claude設定画面でLoku接続を張り直す）
    • 案3：店舗数が増えたらAPIキー直叩きのダッシュボード側バッチ処理に寄せ、MCPは開発・デバッグ専用に限定する
